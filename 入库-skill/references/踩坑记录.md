# 踩坑记录（都是踩过的，别再来一遍）

## 1. CDP 鼠标事件在这台机器上一次 5 秒（最大的坑）

实测：`Input.dispatchMouseEvent`（mouseMoved）单次 **5074ms**。点一下「重置」5 秒，一单点三四下就 20 秒，表面看像「脚本很慢」。

对照：

| 动作 | 耗时 |
|---|---|
| `Input.dispatchMouseEvent` | **~5000ms** |
| `Input.dispatchKeyEvent` | 2ms |
| `Input.insertText` | 18ms |
| JS `el.focus()/select()/click()` | 2ms |
| `Runtime.enable` | 15ms |
| node 冷启动（360 杀软扫描） | ~300ms |

结论：**全程不用鼠标**。聚焦用 `element.focus()`，输入用键盘事件 + `insertText`，点按钮用 `el.click()`。只有排查实在没办法时才用 `dispatchMouseEvent`。

## 2. 值相同时 `insertText` 不触发 onChange

先演练过一次（框里已经是 1），再 `--dry` 或真跑时又输入 1，值没变 → React 的 onChange 不触发 → 组件状态还停在 0 → 提交报 **「收货的本次收货数量必须大于0」**，但输入框明明显示 1。

修法（脚本已内置）：

1. 每次填数**先按 Backspace 清空**，再 `insertText`；
2. 提交前读「本次总退数」硬校验，`Number(foot) !== Number(qty)` 就不点。

## 3. toast 会残留，连收第二单读到的是上一单的

toast 存活 3~5 秒，第二单提交后立即读，读到的可能是第一单的「XXX 退货成功」。

修法（脚本已内置）：提交前先记下屏上已有 toast，提交后**只认发生变化的那条**，并校验文本里含当前单号。

## 4. 界面轮询会假阴性，预检必须走接口

早期用「填单号 → 读表格行数」判断有没有售后单，结果把 4 个其实有售后单的单号报成「查不到」。原因大概是 `重置 → 聚焦 → 输入` 的连招在重渲染期间丢焦点。

结论：**判断有没有售后单只信接口**（`scanning/search/v2`），不要用界面行数推断。

## 5. 部分收货的售后单在聚水潭里仍然查得到

表格写 1 件、申请 2 件，收 1 件后售后单状态变 `Confirmed`，但 `scanning/search/v2` 依然返回它（`qty:2, currentQty:1`）。所以：

- 不能靠接口「还在列表里」判断没入过库；
- 也不能用本地台账判重（会跟涂黄打架）；
- **唯一依据是登记表 A~E 是否已涂黄。**

## 6. 数量框旁边有个单价框，别乱点

`ant-input-number-input` 在商品行里有三个：单价（x≈1187，值 `29.9500`）、本次数量（x≈1388）、次品（x≈1463）。按 x 坐标过滤，或按 placeholder=`次品` 找。

早期按「第一个非次品输入框」取，结果点到单价，还被弹了改价校验，白等十几秒。

## 7. 表格不是 antd table

是 styled-components 的 `art-table`：`tr.art-table-row` / `td.art-table-cell`。`tbody tr.ant-table-row` 会返回 0 行，别用它判断「有没有行」。

## 8. AI 拉起的浏览器会被回收

`Start-Process` 启动的浏览器，命令一结束进程就没了，调试口也随之消失。必须由用户双击启动器：`D:\log\浏览器\2-启动-360安全-9224.bat`（跨工位自适应，自动找浏览器安装位置；不确定本机装了什么先双击 `0-检查本机浏览器.bat`）。

## 9. 表头文字会被虚拟列错位

`thead th` 的坐标跟实际渲染列对不上（`其它仓库数量` 盖住了次品框的位置）。别靠表头定位输入框，靠 placeholder 或固定 x 阈值。

## 10. 换工位要重新确认的三件事

1. 浏览器是谁（本机是 **360 安全浏览器**，QQ 浏览器已不在；换工位先用 `D:\log\浏览器\0-检查本机浏览器.bat` 看实际装了什么）；
2. 调试口端口（不固定，工位不同端口不同，以用户启动浏览器时告知的为准；**9223 归乐言**，别抢）；
3. 扫描帧 URL 里的 `owner_co_id` / `authorize_co_id`（脚本从 URL 现取，一般不用管）。

## 11. `.bat` 必须是纯 ASCII + CRLF

cmd 只认 CRLF，用 LF 会让首字符被吃掉（`setlocal` 变 `ocal`）。PowerShell 5.1 存 `.ps1` 要带 UTF-8 BOM。

## 12. 涂黄：`Internal error` 不是通道问题，是 `xf` 结构写错

`sheet.update_range_data` 传 `opType: "format"` 本身是可用的（2026-11-22 定稿）。连续几次 `ID-XXXX 第三方服务错误：Internal error` 的真实原因只有两个：

1. 颜色对象漏 `tint`（`back: {type:2, value:...}` 就报 Internal error，报错完全看不出是缺字段）；
2. `fill` 写成扁平 `{type:2, value:...}`，`type` 被当成填充类型（见下一条）。

`sheet.range_data_batch_update` 也能用，但字段必须**下划线 + 全称**：`op_type: "cell_operation_type_format"`、`row_from/row_to/col_from/col_to`；驼峰会报 `op_type 为必填`。日常优先 `update_range_data`，`rangeData` 里显式写 `rowFrom/rowTo/colFrom/colTo`，别依赖 `range` 对象。一次塞 10 行比较稳。

## 13. 涂黄变成灰黄斜纹（回读查不出来，最容易翻车）

- 错：`xf: {fill: {type: 2, value: ID-XXXX}}` → `fill.type` 是**填充类型**，2 = 图案填充，单元格渲染成灰黄斜纹，看着像没涂干净。
- 对：`xf: {type:1, fill:{type:1, back:{type:2,value:ID-XXXX,tint:0}, fore:{type:255,value:0,tint:0}}}`。
- **`get_range_data` 回读 `cell_background_color` 一直是 `#FFFFFF00`，斜纹和实心返回一模一样**，所以「回读相等 ≠ 视觉正确」。
- 验收：涂完让用户扫一眼，或截图确认 A~E 底色均匀、无纹理。发现斜纹的行整段重刷（重刷幂等，不会叠加）。

## 14. 「表格没看到黄色」先让用户刷新，再怀疑写入失败

涂完立刻回读 `cell_background_color` 是权威的；用户在金山文档页面里看到的可能是缓存视图，需要刷新表格才变色。别因为一句"没看到黄"就重复涂一遍（虽然幂等，但会浪费一轮往返）。

## 15. 大范围 `get_range_data` 的底色会失真（2026-11-22 实测）

一次读 50 行以上、或多列一起读时，`cell_background_color` 会对部分格子返回默认的 `#FFFFFFFF`，**哪怕单元格实际是黄的**。

实际症状：读 8830–8880（6 列）时，8867/8868/8870 显示白色；把范围缩到 8862–8878、只读 B/C 两列，同样的格子全是 `#FFFFFF00`。同一行不同列也可能一个说黄一个说白。

后果：**用大范围读判断「哪些行还没涂黄」会把已入库的行重新当成待处理**，可能重复收货。

规矩：

- 判「待入库」/ 判「涂没涂上」，一律**小范围读**：≤10 行、只读需要的 1~2 列；
- 想一次看几十行只用来看单号、货号、数量（文本类字段是准的），**不要信那一批的底色**；
- 拿不准就抽查 5 行精确读一次，别凭大范围的底色下结论。
